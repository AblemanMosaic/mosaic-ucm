# Pippi project and process governance

Use the `BUILD_PROCESS_*` surfaces, or `ucm process-build`, when a Pippi campaign spans more than one isolated turn.

## Baseline

Bind the exact subject and source manifest, architecture and AMCAS contracts, standards catalog, policy and requirement roots, software generation, user and session identities, DKN-compatible locality declaration, responsibilities, deliverables, execution capsules and initial journal head. Keep the user identity distinct from the agent/session identity.

A DKN dimension and MosaicID passport are locality and identity commitments. They grant no namespace rights, permission or capability. Carry possession, namespace policy and local admission as separately verified roots.

## Exact execution capsule

Before accepting a terminal receipt as reusable, bind the executable, runner, argv, normalized cwd, declared environment projection, complete execution-critical dependency manifest, exact inputs, policy, profile, authority, jurisdiction, effect class, expected writes, declared transaction-history paths and adapter implementation.

Any changed bound input requires a new operation identity. Each persisted artifact must carry `producer_operation_root`. Different bytes under one identity refuse; successor bytes require a new identity plus predecessor history. Legacy artifacts without producer identity require explicit migration. If dependency completeness cannot be established, record `INCOMPLETE` closure and do not reuse a prior terminal receipt. This is effect/result custody, not an ordinary cache hint.

## Milestones and replanning

- Before implementation, bind each work unit to exactly one acceptance case. A direct step names the exact closure check. Shared infrastructure requires a rooted record proving that same case is blocked by the missing capability, with diagnostic evidence and an unblock criterion. Shared infrastructure completion is a prerequisite result and cannot be recorded as acceptance-case closure.
- Define entry criteria, deliverables, exact required checks, standards obligations, acceptance role and policy, rollback rule and authority ceiling.
- Treat a ready assessment as a request for external acceptance. Only a fresh signed external approval over that assessment can produce an accepted milestone record.
- Keep implemented, tested, reviewed and accepted states separate.
- On replanning, dispose every unresolved work item as retained, resolved or deferred. Distinguish retained evidence from invalidated evidence and preserve the predecessor plan and checkpoint.

## Standards and status

Trigger standards reviews from meaningful events such as architecture change, evidence drift, new capability, recovery, release or handoff. Avoid blind periodic reminders. Project human, agent and forensic views from the same rooted checkpoint and standards schedule. Suggested next actions are navigation only and must carry `authorized: false`.

Export a THR/CAS envelope that keeps exact state (`H_s`), governance and admissibility (`H_c`), declared meaning (`H_m`), locality (`H_j`), receipt identity (`H_r`) and whole-body integrity (`h_body`) distinct. Equality of one commitment never proves the others.

Before courthouse handoff, build a process binding that pins the baseline, current checkpoint, journal head, execution capsule, producer-operation identity, authority policy, jurisdiction and native runner. The binding requires native G1/G2/G3 receipts but remains `dispatch_authorized: false`; only the admitted courthouse adapter can establish effect custody.
