# Portfolio governance

Use one fixed roster for the integration campaign. Each application has one
stable application ID, thread ID, and kit name. Record intake, delivered
instruction, and imported Stage I1 bundle in that order.

Store each exact return in content-addressed storage before journaling the
import. Portfolio readiness requires successful rehash and separated THR
commitments. For Stage I2, require explicit exports and imports from every
session. Do not infer a provider, consumer, semantic owner, executor, schema,
identity, or jurisdiction from similar names. A clean composition preflight is
an input to a correspondence court, never permission to connect systems.

Import each declaration as exact returned bytes and keep its CAS digest,
canonical semantic digest, rooted declaration, revision number, and G1/G2/G3
receipt chain distinct. The latest verified revision is active for preflight.

An export's `consumers` list is an invitation, not consent. A relation is
matched only when the consumer's latest declaration imports the same provider,
interface ID, and schema root. If a consumer declines an invitation, request a
provider successor that removes that consumer. Never rewrite either party's
declaration in the coordinator session.

Every action receives namespaced Sentinel, Witness, and Diagnostic records.
Readiness is computed from the fixed denominator. The portfolio observes and
binds application sessions; it does not grant authority or execute effects.
