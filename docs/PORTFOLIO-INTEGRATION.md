# Multi-application portfolio integration

A roster fixes the campaign denominator: application ID, name, thread ID, and
kit. The portfolio journal records exact intake, instruction, and verified
Stage I1 return for each row. Every action receives namespaced G1, G2, and G3
receipts. Every imported return is rehashed into the content-addressed store.
`portfolio-status` becomes ready for composition preflight only when every
application has a verified Stage I1 bundle, a verified CAS object, and separated
`H_s/H_c/H_m/H_j/H_r` commitments.

Stage I2 never infers provider/consumer edges from route names. Generate one
declaration template per application with `portfolio-composition-template`.
Each session explicitly declares exported interfaces and consumed interfaces,
including schema root, semantic owner, native effect executor, and intended
counterparty. Run `portfolio-composition-preflight` across all exact Stage I1
bundles and returned declarations. Missing declarations, missing providers, or
schema mismatches remain visible obligations. A clean preflight is only ready
for a correspondence court; it does not authorize composition.

The portfolio observes separate sessions. It does not inherit their keys,
execute their effects, or convert a report into authority.
