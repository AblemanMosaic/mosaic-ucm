# AMCAS Migration and Application Profile Playbook

## Contract evolution

1. Preserve the predecessor contract and root.
2. Produce an exact semantic diff.
3. Classify added, removed, and changed requirements, capabilities, effects, dependencies, realization axes, constraints, and acceptance criteria.
4. Treat every authority-adjacent change as requiring explicit review.
5. Compile the successor and discharge every emitted migration obligation.
6. Keep old journals anchored to the old root. Continue only through an explicit successor receipt; never rewrite history.

## Profiles

- **AUTHORING** exposes pure and read-only planning surfaces.
- **OPERATIONAL** exposes the application capability projection but still grants no permission. Effects require the operational gateway.
- **VERIFY_ONLY** exposes pure and read-only verification surfaces.
- **COMPATIBILITY** contains only explicitly retained legacy routes.

A profile set binds the exact Stage I3 plan, AMCAS registry, UCM coverage registry, capability set, and native-authority-preservation statement.

## Application intake

Seven frozen Stage I3 application plans have generated profile sets. Mosaic UI, Mosaic Terminal UI, and Mosaic Vocal Lab require Stage I1 intake before profiles can be generated. The historical `MOSAIC.2D_3D` identity must be rebound to its World Engine successor; the observatory records that obligation rather than guessing identity continuity.

## Semantic consolidation

Candidate common primitives are proposals until human/FSC judgment and correspondence evidence establish equivalence. Shared contracts and adapters are preferred before shared effectful services. Native authority and application-specific semantics remain distinct. The portfolio observatory reports exact roots, declared gaps, consolidation campaign roots, and intake or rebinding holds.
