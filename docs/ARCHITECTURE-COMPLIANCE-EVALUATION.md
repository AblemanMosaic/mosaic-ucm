# Architecture-compliance evaluation

Internal determinism does not prove that UCM improves application development.
Track C therefore compares three matched arms: ordinary repository context, strong
conventional enforcement, and UCM-governed work.

The checked-in pilot is now executable study material rather than synthetic roots.
It binds an exact reference-data-client starter tree, task prompt, architecture
contract, scoring rubric, human-oversight policy, three isolated arm contexts, and a
six-run roster: two repetitions in each arm. Before any kit can be issued, the
operator must seal one execution-context registration containing the actual model,
settings, environment, and shared toolchain roots with no undeclared deviations.
`tools/build_architecture_study_kits.py --execution-context <registration>` then
produces one sealed kit per registered run without invoking a model. A kit contains
only its own arm context, so a run cannot learn the other condition labels from its
package.

The protocol pre-registers exact tasks, architectural obligations, model and
human-oversight policies, metrics, denominators and artifact capture. Every arm
uses the same tool affordances; its treatment contract lists the exact condition
materials and translation rule. Each run must complete the same checked-in follow-on
task under the same registered context and return a follow-on result root. Primary
measures are architectural violations, review/repair time, unrelated changes, false
refusals, authoring cost, follow-on drift, ceremony time, and final functional
quality. Reviewers should be blind to condition where feasible.

A completed run must return the registered run ID, exact model, model-settings,
environment, toolchain, unique executor-session and oversight roots, plus output and
review roots and the complete metric set. A blinded score binds the pre-registered
rubric and distinct scorer identity/session roots. Aggregation refuses a missing,
duplicate, substituted or extra run, reused executor or scorer sessions, or unmatched
model/settings/environment/toolchain roots. Even a complete aggregate
is labelled `OBSERVED_NOT_CAUSAL_CONCLUSION`; it is not statistical significance,
a generalized benefit claim, or deployment authority.

Application architecture contracts may require both functional-test roots and
verified Native Proof Kernel result roots. The architecture checker binds those
receipts but does not rerun either test programs or proofs. This keeps source
architecture policy, execution evidence, and deductive proof as separate claims.
