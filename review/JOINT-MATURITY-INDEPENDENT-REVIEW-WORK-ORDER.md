# UCM unified maturity successor — joint independent-review work order

## Boundary

Review the exact qualification-source archive, canonical-software archive,
four profile overlays, qualification receipt, self-release campaign, and operator-court evidence named
by the final freeze receipt. Do not infer authority from a filename, human-readable
version, Git branch, or earlier review. The subject remains `INFORMATION_ONLY`,
with authority effect `NONE`, real A5 false, and G0 closed.

The successor has three separately reportable tracks:

1. **UCM product maturity:** authoring, compatibility, operational, and verify-only profiles;
   evolution, linting, lifecycle, journal intelligence, diagnostics, proof,
   deterministic packaging, and the consolidated hardening boundary.
2. **Mosaic ecosystem integration:** exact imported seven-application baseline,
   exact application-authored and pipeline-bound Stage I3 plan generations,
   a zero-semantic-change rebind reconciliation, append-only later audit returns,
   exact coherent repair-successor returns, a derived current-state register,
   and coherent batch repair programs,
   governed work packages, AMCAS/CM1/CM2 correspondence, and non-authorizing
   MosaiCOS M1 preparation.
3. **Empirical architecture proof:** pre-registered comparison protocol, fixed
   denominator, exact run bindings, and results that must not overclaim causality.

## Carried Track A reviews and repair claims

The qualification source carries two exact, non-interchangeable reviews under
`review/unified-maturity/track-a/`: a passive semantic review and an executed
positive/static review. Verify both archives against `REVIEW-REGISTER.json` and
apply its severity-preserving union. A positive replay does not close a finding
from the passive review.

`REPAIR-DISPOSITION.json` is a builder claim only. Independently determine whether
UMR-P1 through UMR-P5, UMR-C1, and UMT1-01 are closed. In particular, exercise
profile enforcement, read-only inspection, exact architecture evidence, terminal
history rederivation, post-G2 finalization without redispatch, the registered
study execution context and follow-on task, and the Stage I3 rebind provenance.

## Tier 0 — custody and happy path

1. Verify every outer and nested archive using the shipped standard-library
   verifier and the freeze-receipt hashes.
2. Rebuild the qualification source twice and compare its source root, member set,
   and bytes with the receipt.
3. Decode the canonical software archive. Confirm that policy packs, conformance
   vectors, study protocol, ecosystem baseline, M0 fixture, program ledger, and
   profile manifests are present.
4. Recompute the capability registry and all four surface-set roots. Confirm that
   profiles only remove surfaces and never broaden the authority ceiling.
   Confirm that legacy surfaces appear only in the explicit compatibility profile.
5. Verify the exact historical Stage I3 pipeline release `3c549fbc...` carried
   in the handoff and qualification source, then confirm all seven retained
   pipeline-bound records name that exact archive. Treat it as generator custody,
   not current execution authority.
6. Run the positive/static qualification from a clean extraction on CPython 3.12
   and 3.13. It must preserve exact test identities, have zero failures/errors/skips,
   and rebuild all deterministic archives byte-for-byte.
7. Confirm the canonical runtime orients, reports field diagnostics, validates the
   architecture reference, and keeps MosaiCOS identities, targets, network access,
   and operational authority unbound.
8. Rebuild the UCM self-release campaign from the frozen source campaign and
   qualification. Confirm the 56-requirement denominator, external-tool evidence
   binding, requirement dispositions, journal chain, and campaign summary. The
   campaign must remain pending operator Tier 1 and independent review.
9. Inspect the contract authoring profile, contract doctor, semantic/domain diff,
   selection explanation, strict agent adapter, ordinary-tool evidence adapter,
   ABI table, environment policy, time policy, completions, and non-authoritative
   pretty projections through their public surfaces.
10. Verify the P/PPI r004 consolidation as a delivered product boundary: the
    command launcher, native Mosaic UI dependency closure, global hub, session
    migration, process governance, review-custody lifecycle, skill, installer,
    and public CLI must all resolve from the exact runtime bytes.
11. Build the public release twice. Confirm that runtime, SDK, review custody,
    and lineage archives are byte-identical across builds. Runtime and SDK must
    exclude ecosystem return packages and review evidence; those bytes belong
    only to the separately identified review archive.
12. Extract the runtime into a fresh directory and verify it with its own
    standard-library verifier before exercising `PIPPI.cmd --help`, native UI
    loading, onboarding, and project verification. Installation must stage an
    immutable r004 runtime and must not copy credentials into P/PPI storage.
13. Verify the canonical transtemporal archive policy. Runtime and SDK must
    refuse all inline review, operator, and integration-return custody paths.
    The review archive must declare `SELF_CONTAINED_CUSTODY` and equal the
    complete fixed denominator. Recompute semantic, state, metadata,
    governance, and whole-reference roots; confirm an unavailable object yields
    `HOLD_FOR_ARCHIVE_AVAILABILITY`; and confirm repeated references report
    logical versus unique physical bytes without storing duplicate objects.

Any MED or HIGH happy-path failure blocks the joint recommendation. LOW hardening
findings should be batched unless they undermine a claimed happy-path invariant.

## Tier 1 — consolidated adversarial boundary

Run the sealed operator kit from a disposable directory and independently inspect
the results. The operator run is useful engineering evidence; a terminal independent
verdict still requires reviewer control of the review leg.

Cover these families as a batch:

- malformed and noncanonical inputs;
- cross-record and cross-subject binding substitutions;
- profile bypass and capability broadening;
- stale, future, wrong-policy, and wrong-subject evidence;
- path portability, aliases, and archive-set closure;
- interruption/recovery and journal-chain divergence;
- selective reporting and fixed-denominator removal;
- consistently re-sealed contracts, manifests, profiles, courts, and evidence.
- authoring profiles that compile to vacuous or authority-broadening contracts;
- undeclared contract migrations and superseded-root laundering;
- wrong agent registry/profile pins and compatibility-route selection;
- external approval signature, subject, policy, and freshness substitutions;
- external-tool evidence cross-subject and cross-policy substitutions;
- policy-pack collisions and conflicting shared requirements;
- canonical JSON edge cases, environment overrides, and completion/registry drift;
- dogfood campaign denominator removal, evidence swapping, and journal divergence.
- Pippi context, draft, decision, projection, and turn cross-binding substitutions;
- undeclared effect laundering and proposal-disposition denominator shrinkage;
- semantic-passage UTF-8 span, exact-text, vocabulary, integer, and provider-root swaps;
- development-standards fixed-denominator and check-subject substitutions;
- constitutional-launch readiness-evidence and state-transition bypasses;
- behavioral-harness undeclared controls, write paths, scenarios, and executor receipts.
- P/PPI review-envelope subject, work-order, replay, return, and publication-hold
  substitutions, including a verdict that does not match its exact subject;
- runtime-manifest mutation, missing native UI resources, immutable-revision
  collisions, incomplete install staging, and runtime/SDK review-byte leakage;
- implicit version/revision changes, secret-shaped onboarding inputs, stale
  project heads, duplicate projects, and migrated-session source rewriting.

For the architecture subsystem, distinguish test roots from verified Native Proof
Kernel roots. For the evaluation subsystem, refuse missing or duplicate runs and
report only `OBSERVED_NOT_CAUSAL_CONCLUSION`. For MosaiCOS, no mutation may convert
an unbound preparation into a target, identity, network, execution, or acceptance
claim.

## Tier 2 — replay policy

The builder performs one cache-free positive/static qualification for the large
candidate. A reviewer should run a fresh qualification only when Tier 0 or Tier 1
exposes drift, missing inputs, uncertainty, platform dependence, or an unverifiable
receipt. Do not replay historical archives merely because they are historical; use
their exact pins unless a trigger makes them relevant.
